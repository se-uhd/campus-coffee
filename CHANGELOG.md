## [0.5.6] - 2026-07-03

- Add an event-sourced revert: `POST /api/{pos,users,reviews}/{id}/revert?version={v}` undoes an entity's last recorded change by appending a compensating event and projecting it, in one transaction, so the log stays append-only and only the read model changes. The compensation depends on the last event: a creation is undone by a `DELETE` (the resource is removed, `204`), an update by re-applying the immediately preceding snapshot (`200` with the restored resource). Because the compensation is itself an event, reverts stack (reverting a revert re-applies the change), and the projection reuses `ReadModelProjector`, so a revert inherits the same invariants as any write (undoing the creation of a still-referenced POS is a `409 DeletionConflictException`). The capability is exposed through the domain ports (`CrudService`/`CrudDataService.revertLastChange`) and implemented in the data layer by a new `EventSourcedReverter` (modeled on `EventSourcedWriter`) plus a per-entity `EventRepository.findByEntityTypeAndEntityIdOrderBySeqAsc` history query (using the existing `body ->> 'id'` index; no migration). The relational adapter has no log and rejects the operation with a `400 ValidationException`. Reverting a review's approval-driven change is refused (`400`), since the approval state is owned by the approval workflow, not by an edit; only text edits are revertible.
- Guard the revert against lost updates with optimistic concurrency. Reverting is a read-modify-write, so the client sends the `version` it observed and the server reverts only if the entity's current version still matches, else returns `409 ConcurrentUpdateException`. The optimistic-locking `@Version` counter (already on `pos`/`users`/`reviews`) is now exposed as a read-only `version` on the domain models and DTOs to carry that handle. It is kept out of the event bodies (a read-model counter, not recorded state), alongside the raw password and the flattened review references.
- Gate the revert endpoints by the existing role matrix: a POS revert requires `MODERATOR` (via the existing `/api/pos/**` rule), a review revert `MODERATOR`, and a user revert `ADMIN` (like deleting a user). Covered by data-layer integration tests (`EventSourcedReverterTest`, all three compensation cases plus the version guard, deletion conflict, and revert-of-revert), the relational rejection (`CrudDataServiceRevertTest`), and system tests over HTTP in both modes (`RevertSystemTests`, `EventSourcingRevertSystemTests`). Design notes in `doc/2026-07-01_revert-last-recorded-change.md`.
- Lift the revert endpoint's shared body into the generic `CrudController`. The `revert` handler was identical in `PosController`, `UserController`, and `ReviewController` (call `revertLastChange`, return `200` with the mapped resource, or `204` when the compensation removed it); it now lives in an `open CrudController.revert` with no HTTP mapping, so it stays opt-in like the other base methods. The three controllers keep their own `@PostMapping` and OpenAPI annotations and delegate to `super`, so the per-resource docs and response schemas are unchanged. `RevertSystemTests` passes in both persistence modes.

## [0.5.5] - 2026-06-29

- Type the event-sourcing decorators' `delegate` against the domain port instead of the concrete relational `*Impl` (e.g., `PosDataService` rather than `PosDataServiceImpl`), so a decorator and the adapter it wraps share only the interface, the relationship the Decorator pattern relies on. Each relational adapter declares an explicit `@Service(BEAN_NAME)` bean name, and the decorator pins its delegate to that bean with `@param:Qualifier(<Impl>.BEAN_NAME)`. Without the qualifier, Spring would select the `@Primary` decorator as its own delegate. Behavior and wiring are unchanged, and the relational and event-sourcing wiring tests pass in both modes.

## [0.5.4] - 2026-06-24

Includes a round of hardening and correctness fixes from an adversarial review of the repository.

- Stop the prod profile from seeding committed admin credentials by default. The prod profile defaulted `campus-coffee.fixtures.load-on-startup` to `true`, so a fresh prod database came up with the fixture users, whose passwords are committed in `TestFixtures` (a known-credentials login as a full admin against the public `/api/auth/token`). The prod default is now `${LOAD_FIXTURES_ON_STARTUP:false}`; seeding the demo data is an explicit opt-in (`LOAD_FIXTURES_ON_STARTUP=true`, documented in `deploy.env.example` as throwaway-demo-only). The dev profile still loads the fixtures on startup.
- Remove the in-source JWT fallback secret from the always-applied base config. The base document set `campus-coffee.jwt.secret` to a committed fallback, so every non-prod run (including the no-profile bare image) signed and verified tokens with a public key, letting anyone mint an admin bearer token. The base now requires `JWT_SECRET` with no default (so a no-profile or prod run fails fast when it is unset); the dev profile sets a fixed insecure secret directly (a plain value, no env-var indirection). The test suite already supplies its own secret via a system property, so the test bootstrap is unaffected.
- Keep the dev data endpoints open for convenient local testing, but make them strictly dev-only. The `DevController` is registered only in the dev profile, yet `SecurityConfig` opened `/api/dev/**` with an unconditional `permitAll` present in every profile. The `permitAll` rule is now added only when the dev profile is active, so it stays coupled to the controller's profile scoping and `/api/dev/**` is never opened in a deployed profile. The endpoints stay unauthenticated in dev (clearing and reloading the fixtures should not need credentials during development), and the dev profile must not run on a network-reachable host. `DevDataNotInDeployedProfileSystemTests` asserts `/api/dev/data` returns `404` outside the dev profile.
- Add optimistic locking versions to `pos` and `users` (`V9` migration plus `@Version` on `PosEntity`/`UserEntity`), so a concurrent update to the same POS or user surfaces as a `409 ConcurrentUpdateException` instead of silently overwriting the earlier change, matching reviews. All three version fields default to `0` (not null), including `ReviewEntity` (changed from null for consistency): a null version makes Hibernate read a detached copy built by the mapper as a transient instance and reject a `@ManyToOne` to it (a review references its POS and author), so the non-null default keeps such a reference treated as detached.
- Retry a concurrent review approval instead of dropping it. Two different users approving the same review at once both wrote the versioned review row, so one lost the optimistic locking race and its just-recorded approval rolled back. `ReviewServiceImpl.approve` now runs each attempt in its own transaction (`TransactionTemplate`) and retries on `ConcurrentUpdateException`, so both approvals land; a repeat by the same user still fails fast on the unique constraint. A new `ReviewApprovalConcurrencyTest` (both persistence modes) drives two concurrent approvals and asserts the count stays consistent.
- Validate the POS `street` length and the house-number format at the API boundary. `PosDto.street` now carries `@Size(max = 255)` (the `varchar(255)` column previously overflowed to a `500` instead of a `400`), and the house-number pattern (DTO `@Pattern` and the domain `Pos`) rejects a leading zero or a separator (`"007"`, `"21-a"`), which the numeric/suffix split would otherwise silently drop on the persistence round-trip. `PosSystemTests` asserts the over-length `400` and that a `PUT` advances `updatedAt` in both modes.
- Map a malformed OSM tag to a `502` and parse a lone tag. `OsmResponseDeserializer` read `k`/`v` with a non-null-safe `asText()`, so a tag missing an attribute threw a raw `NullPointerException` (a `500`), and a single `<tag>` (rendered as an object, not an array) was dropped. It now treats a missing `k`/`v` as a malformed response (`ExternalServiceException`, `502`) and collects a lone tag.
- Make a `PUT` advance `updatedAt` in relational mode even for a no-op update, matching the event-sourcing projector (which always writes a fresh `updatedAt`), so the two persistence modes have identical observable update semantics.
- Refuse an events-to-data rebuild that cannot replay a populated read table. The rebuild skipped only a fully empty log; a partially populated log (reachable after flipping `persistence.mode`) cleared the tables and silently lost the rows of any type the log had no events for. It now fails loudly when a read table holds rows of a type the log cannot replay. A new `EventsToDataRunnerTest` case covers it.
- Make the event-sourcing decorators the wired default when the mode key is absent (`matchIfMissing = true`), so the conditional wiring agrees with the `PersistenceProperties` default (`EVENT_SOURCING`) and the runners.
- Backfill the base `USER` role for pre-existing users in `V7`, so an in-place upgrade of a database from the earlier exercises leaves users with a usable role set instead of none (their password must still be reset; a password cannot be backfilled).
- Close two test-harness and tooling gaps the review found: the ArchUnit layered test left `application.configuration` (`FixturesProperties`) in no layer, so `mayNotBeAccessedByAnyLayer()` did not protect it — the application layer now matches it recursively and `ensureAllClassesAreContainedInArchitecture()` fails on any unassigned production class; and `scripts/check-version-sync.sh` now compares the full version token (including any pre-release suffix) instead of only `x.y.z`.
- Gate the Actuator `env` endpoint behind ADMIN. It is exposed only in the dev profile, where `SecurityConfig` had no rule for it, so a `GET /actuator/env` fell through to the public read catch-all and was served anonymously. Add `authorize("/actuator/env", hasRole("ADMIN"))` (and `/env/**`) to match the `metrics` rule, and fix the comment that conflated exposure with authorization. `ActuatorSecuritySystemTests` asserts the health/metrics/env access matrix (covering the previously untested `metrics` rule too), and `INSTRUCTOR.md` documents env as ADMIN-only.
- Make the system-test harness robust without fork-level parallelism. `SystemTestUtils.configureClient` rebuilt a `RestTestClient` on every test and never disposed the old one. Under `-PtestForks=1` (all system-test contexts cached in one JVM, each on its own random port) the suite accumulated a client with its own connection pool per test, hundreds at once, and the crossed connections showed up as wrong-port `ResourceAccessException`s (an HTTP request reading a non-HTTP response). Cache one client per server port (`computeIfAbsent`) so each test uses its own context's client and the live clients are bounded to one per context. The full suite now passes under `-PtestForks=1` as well as the default fork-level parallelism.
- Move the entire Spring Security setup out of the `application` module into a new `api/security` package, on the principle that the api module is the application's interface to the outside world and the access rules define that interface. This covers the adapters — the JSON 401 and 403 writers (`JsonAuthenticationEntryPoint`, `JsonAccessDeniedHandler`, which build the api `ErrorResponse`) and the `UserDetailsService` implementation, renamed from `CampusUserDetailsService` to `DomainUserDetailsService` — and the configuration: `SecurityConfig` (the filter chain and the URL→role authorization matrix), `JwtConfig` (the JWT encoder and decoder), and `JwtProperties`. They join the existing `CurrentUserProvider`, so `api/security` is the single home for the Spring Security integration. The move makes api self-contained: its `AuthController` consumes the `AuthenticationManager` and `JwtEncoder` beans that previously lived in `application`. `application` is left as bootstrap only — the Spring Boot entry point, the startup tasks, and `FixturesProperties` — with no dependency on api internals. `SecurityConfig` references the actuator paths as plain strings, so api needs no actuator dependency. The ArchUnit application layer drops the now-empty `security` package. Behavior and tests are unchanged.
- Rename `ApiPathConfig` to `ApiWebConfig`. The class is a `WebMvcConfigurer` that does more than the base path: it also drops the XML message converter and pins the JSON charset to UTF-8, so "Web" names its scope. No behavior change.
- Improve the docs. Expand the README `Authentication and authorization` section with both authentication mechanisms (HTTP Basic and the JWT bearer flow, the latter not previously shown in the README), the role model, and the full access matrix. Bring the README Cloud Run deployment docs in line with `scripts/deploy-cloudrun.sh`: the pre-deploy confirmation prompt that prints the resolved target, the `--project` override, and the `-y`/`--yes` flag. Split the multi-command `curl` blocks in `README.md` and `INSTRUCTOR.md` so each independently run request sits in its own fenced block. Correct stale facts found in an audit of the docs against the code: the Spring Boot version in `CLAUDE.md` (`4.0.6` → `4.1.0`), the missing `ForbiddenException` (403) in its domain-exceptions list, and two README Docker notes that claimed the `dev`-profile container comes up with an empty database (the dev profile loads the fixtures on startup).
- Add `prepare-submission.sh`, the script the assignment tells students to run to package their solution. It zips the repository (keeping `.git/` and excluding build artifacts, IDE files, and the mise-provisioned Gradle wrapper) into a correctly named archive in the parent directory, then validates the unzipped tree the way graders do (`mise install && gradle build`, degrading to a warning when mise or Docker is unavailable).

## [0.5.1] - 2026-06-22

- Run the `:application:test` suite (the system, acceptance, and architecture tests, the slow part of the build) in parallel across several JVM processes to speed it up. `maxParallelForks` on the `application` `test` task now defaults to `min(4, availableProcessors / 2)` (override with `-PtestForks=N`; `-PtestForks=1` disables parallelism), with a `1g` per-fork heap cap so the forks cannot collectively overcommit. Process-level forking is the only safe form of parallelism here: `SystemTestUtils` is an `object` with a shared mutable `RestTestClient` and the test bases wipe the whole database between tests with `clearAll()`, so two tests must never run concurrently in the same JVM or against the same database. Each fork is a separate JVM with its own `SystemTestUtils` and its own Testcontainers PostgreSQL instance (the container lives in a companion object, one per JVM), and JUnit runs the classes within a fork serially, so two tests never touch the shared client at once and `clearAll()` never wipes a running test's data, while Spring's per-JVM context cache still pays off within each fork. On a 16-core machine this took the task from ~95s to ~50s with all 145 tests still passing.

## [0.3.0] - 2026-06-19

- Make the seeded `IdGenerator` thread-safe: `SeededUuidGenerator.newId()` and `reset()` are now mutually exclusive under a lock, so a `reset()` running concurrently with id generation (for example the dev `PUT /api/dev/data` reload while a write is in flight) cannot hand out an id from a half-replaced generator, and the deterministic id sequence holds under concurrency.
- Add a configurable event sourcing (event-first CQRS) persistence mode, selected by `campus-coffee.persistence.mode` (`relational`, the default, or `event-sourcing`). In event sourcing mode the append-only event log is the source of truth and the relational tables are a read model projected from it: each write request assigns the id and timestamps, appends one full-state event, then projects it into the tables in a single transaction, so a uniqueness, foreign key, or optimistic locking violation rolls both back and the log never holds an invalid event. The relational data adapters are wrapped by event-sourced decorators (`@Primary` and `@ConditionalOnProperty` when the mode is on), so the `domain` and `api` layers are unchanged and read requests are served from the materialized tables. The projection reuses the existing MapStruct mappers and writes the id and `createdAt`/`updatedAt` from the event body verbatim (a transient flag suppresses the JPA timestamp callbacks). A new Flyway migration (`V8`) adds the always-present `events` table (a `jsonb` body serialized through one Jackson mapper, the same one Hibernate binds to the column). Two opt-in startup flags migrate between the representations: `data-to-events-on-startup` appends one INSERT event per existing row (adopt a relational database into the log, idempotent per type), and `events-to-data-on-startup` clears the tables and replays the whole log (rebuild the read model, event sourcing mode only). The event bodies never carry a raw password, and a review event stores its POS and author as ids so no `passwordHash` leaks through a review; a user event keeps the `passwordHash`, so a login survives a rebuild. Event ids come from a separate seeded generator, so enabling event sourcing leaves the deterministic entity ids unchanged.
- Migrate entity ids from database-generated `Long` sequences to application-assigned `UUID`s. A new `IdGenerator` domain port assigns the id in the data-layer insert path before the write, so a null id still means "create" and a non-null id means "update". The generator is selected by `campus-coffee.id.seed`: a numeric seed (the default) makes the assigned ids deterministic and reproducible, so the loaded fixture data has stable ids the README and instructor demo can reference (loaded on startup in the `dev` and `prod` profiles, and reloadable via `PUT /api/dev/data` in `dev`). Setting it to `random` (`CAMPUS_COFFEE_ID_SEED=random`) uses random UUIDs. The base JPA entity now implements Spring Data's `Persistable<UUID>` with an explicit transient new-entity flag, so `repository.save()` inserts a freshly built entity without a preceding SELECT. The custom sequence-generation and sequence-reset machinery (`CustomSequence`, `ResettableSequenceRepository`, `JpaUtils`) is removed, and the Flyway migrations carry `uuid` primary and foreign keys with no sequences. The OpenStreetMap node id stays a `Long` (it is an external id).
- Load the fixture dataset on startup in the `dev` profile too (not only `prod`), so the local app comes up with the seeded fixture data ready (when the database has no users yet). Use the `/api/dev` endpoints to inspect, reload, or clear it.
- Restrict the Spring Boot Actuator endpoints. `/actuator/health` stays publicly readable (it reports only an `UP`/`DOWN` status, no component detail), `/actuator/metrics` now requires `ADMIN`, and the access rules precede the public `GET` catch-all in `SecurityConfig` so the catch-all no longer exposes them anonymously. The `prod` profile drops `env` from the exposed set, so the environment endpoint is unreachable in production (it stays exposed in `dev`).

## [0.2.0] - 2026-06-17

- Add authentication and authorization. Every write request requires an authenticated principal; the POS directory and reviews stay publicly readable, while user data (login names, emails, roles) is readable only by that user or an `ADMIN` (listing all users is admin-only). Authentication is stateless via HTTP Basic or a JWT bearer token, both resolving to the same principal (login name + `ROLE_*` authorities); `SecurityConfig` disables CSRF and server-side sessions and renders auth failures as the app's JSON `ErrorResponse` (`401`/`403`). A new Flyway migration (`V7`) adds the `password_hash` column and the `user_roles` table, and passwords are hashed with BCrypt via a `CampusUserDetailsService`.
- Add the three independent roles `USER`, `MODERATOR`, and `ADMIN` (no hierarchy): POS curation requires `MODERATOR`, deleting a user requires `ADMIN`, and every other write request requires a login. `USER` is the base role, granted at registration and always retained — an admin may grant or revoke `MODERATOR`/`ADMIN` but cannot strip `USER`. Registration is open and always yields a plain `USER`, so a client cannot self-assign a privileged role.
- Derive the acting user from the authenticated principal instead of the request body: a `CurrentUserProvider` in the `api` layer turns the login name into a domain `User`, so `POST /api/reviews` takes its author and the approve endpoint its approver from the caller (the `authorId` body field and the `user_id` query parameter are gone, and a body still carrying `authorId` is rejected with `400`). Per-target rules live in the domain via a new `ForbiddenException` (mapped to `403`): a review's author or a `MODERATOR` may edit/delete it, a user edits only their own account (an admin edits anyone), and a non-admin may read only their own user record.
- Enforce one approval per user, closing the previously documented repeated-approval hole: approvals are recorded per user (a `ReviewApproval` keyed by review and approver), so a user cannot approve the same review twice (`409`) and cannot approve their own review (`400`).
- Add a stateless JWT bearer-token flow: `POST /api/auth/token` exchanges credentials for a short-lived (15-minute) HMAC-signed token whose `roles` claim maps to authorities, so the same authorization rules apply under Bearer as under Basic. The signing secret comes from `JWT_SECRET`; the `dev` profile has an insecure fallback, while the `prod` profile has none (startup fails if it is unset).
- Require a password on registration (minimum 8 characters, scoped to a create-only Bean Validation group so updates may omit it and keep the stored hash); no response ever serializes a password or hash.
